# 健康管理マスター API設計書案 v0.2

## 1. ドキュメントの目的

本ドキュメントは、健康管理マスターにおけるAPI設計方針を整理するための資料である。

本ドキュメントでは、フロントエンドとバックエンドの境界として、以下を定義する。

* API全体の設計方針
* API一覧
* 画面とAPIの対応
* 認証が必要なAPIの扱い
* リソースごとのAPI概要
* 共通ステータスコード方針
* 共通エラー方針
* 詳細スキーマの管理方針

個々のリクエスト項目、レスポンス項目、型、DTO、バリデーション詳細は、本ドキュメントでは細かく管理しない。
詳細なAPI仕様は Swagger / OpenAPI を正とする。

---

## 2. API設計書の位置づけ

本ドキュメントは、Swagger / OpenAPI の代替ではない。

Swagger / OpenAPI は、以下を管理する正本とする。

* エンドポイント
* HTTPメソッド
* query parameter
* request body
* response body
* schema
* status code
* 認証スキーム

本ドキュメントでは、Swaggerだけでは把握しにくい以下の内容を整理する。

* なぜそのAPI構成にするか
* どの画面がどのAPIを利用するか
* APIをどの粒度で分割するか
* 未登録データの扱い
* 削除APIの扱い
* 認証済みユーザーの扱い
* レスポンスに内部情報を含めるか
* API変更時の影響範囲

---

## 3. API基本方針

## 3.1 API形式

APIはREST APIとして設計する。

主なリソースは以下とする。

* 食事記録
* 体調記録
* 筋トレ記録
* 履歴

## 3.2 API Prefix

APIの共通prefixは以下とする。

```text
/api
```

## 3.3 データ形式

リクエストおよびレスポンスの基本形式はJSONとする。

```http
Content-Type: application/json
```

## 3.4 日付形式

APIで扱う記録日は、原則として以下の形式とする。

```text
YYYY-MM-DD
```

例：

```text
2026-07-08
```

JST午前5時境界による「今日の記録日」の算出は、画面仕様およびフロントエンド側の日付処理で扱う。
APIでは、渡された `YYYY-MM-DD` を記録日として扱う。

DB上の日付保持方法、タイムゾーン変換、日付型の扱いはデータ項目定義書または状態管理・データフロー設計書で扱う。

## 4. 認証・認可の前提

記録系APIは、認証済みユーザーのみ利用できる。

認証が必要なAPIでは、フロントエンドから認証情報を送信し、バックエンドで認証済みユーザーを特定する。

方針は以下とする。

* 記録系APIは認証必須とする
* フロントエンドは認証済みトークンをAPIリクエストに付与する
* バックエンドはトークンを検証する
* バックエンドは検証済みトークンからユーザーを特定する
* `userId` はリクエストbodyやquery parameterから受け取らない
* 利用者は自分の記録のみ取得・更新・削除できる

## 4.1 認証スキーム

認証必須APIでは、HTTP AuthorizationヘッダーにCognito Access Tokenを付与する。

```http
Authorization: Bearer <access_token>
```

ID Tokenはバックエンドへ送信しない。API認可にはAccess Tokenのみを利用する。

## 4.2 `X-User-Id` ヘッダーの廃止

初期のローカル開発で仮認証として利用していた `X-User-Id` ヘッダーは**廃止済み**である。

```text
廃止:
X-User-Id ヘッダー
X-User-Id を前提とした仮AuthGuard
X-User-Id 前提のSwagger定義
```

ローカル開発においても実際のCognitoを利用し、認証を迂回する経路を残さない。

CORSの許可ヘッダーは `Content-Type` と `Authorization` のみとする。

認証方式、Cognito連携、JWT検証、トークン管理、認証エラー時の画面遷移は、認証・認可設計書で扱う。

## 7. リソース別API概要

## 7.0 認証API

認証APIは、認証済みユーザー自身の情報を返すためのAPIである。

| API ID  | 用途            | 入力概要 | 出力概要                |
| ------- | ------------- | ---- | ------------------- |
| API-002 | 認証済みユーザー情報取得  | なし   | `id` / `email` / `name` |

設計方針：

* 入力として `userId` を受け取らない。Access Tokenから解決した認証済みユーザーを返す
* `cognitoSub` は外部認証IDであり、画面表示に不要なためレスポンスへ含めない
* `name` はUserInfoで取得できなかった場合 `null` を返す
* 認証疎通の確認と、フロントエンドでの表示名参照に用いる

---

## 7.1 食事記録API

食事記録APIは、指定日の食事記録を取得・保存するためのAPIである。

| API ID  | 用途            | 入力概要       | 出力概要                |
| ------- | ------------- | ---------- | ------------------- |
| API-101 | 指定日の食事記録取得    | 記録日        | 食事記録。未登録の場合は `null` |
| API-102 | 指定日の食事記録登録・更新 | 記録日、食事記録内容 | 保存後の食事記録            |

設計方針：

* 食事記録は1日1件とする
* 同一日の保存は新規追加ではなく登録・更新として扱う
* 認証済みユーザーの食事記録のみ扱う
* 詳細な項目、型、単位、必須/任意はデータ項目定義書およびSwagger / OpenAPIで管理する

---

## 7.2 体調記録API

体調記録APIは、指定日の体調記録を取得・保存するためのAPIである。

| API ID  | 用途            | 入力概要       | 出力概要                |
| ------- | ------------- | ---------- | ------------------- |
| API-201 | 指定日の体調記録取得    | 記録日        | 体調記録。未登録の場合は `null` |
| API-202 | 指定日の体調記録登録・更新 | 記録日、体調記録内容 | 保存後の体調記録            |

設計方針：

* 体調記録は1日1件とする
* 同一日の保存は新規追加ではなく登録・更新として扱う
* 認証済みユーザーの体調記録のみ扱う
* 体調スコアの意味、数値範囲、単位はデータ項目定義書およびバリデーション・エラー設計書で扱う

---

## 7.3 筋トレ記録API

筋トレ記録APIは、指定日の筋トレ記録を取得・保存するためのAPIである。

| API ID  | 用途             | 入力概要      | 出力概要                 |
| ------- | -------------- | --------- | -------------------- |
| API-301 | 指定日の筋トレ記録取得    | 記録日       | 筋トレ記録。未登録の場合は `null` |
| API-302 | 指定日の筋トレ記録登録・更新 | 記録日、筋トレメモ | 保存後の筋トレ記録            |

設計方針：

* 筋トレ記録は1日1件とする
* 当面は自由テキストとして扱う
* 同一日の保存は新規追加ではなく登録・更新として扱う
* 認証済みユーザーの筋トレ記録のみ扱う
* 種目、重量、回数、セット数の構造化管理は今回対象外とする

---

## 7.4 履歴API

履歴APIは、月次履歴および日次詳細を表示するためのAPIである。

| API ID  | 用途             | 入力概要 | 出力概要             |
| ------- | -------------- | ---- | ---------------- |
| API-401 | 指定月の記録あり日付一覧取得 | 年、月  | 記録が存在する日付一覧      |
| API-402 | 指定日の日次詳細取得     | 記録日  | 食事・体調・筋トレ記録のまとまり |
| API-403 | 指定日の日次記録一括削除   | 記録日  | 削除結果             |

設計方針：

* 月次履歴では、食事・体調・筋トレのいずれかが存在する日付を返す
* 日次詳細では、食事・体調・筋トレをまとめて返す
* 各記録が存在しない場合は、該当項目を `null` とする
* 日次削除は、食事・体調・筋トレをまとめて削除する
* 個別削除は今回対象外とする

---

## 8. 未登録データの扱い

指定日の記録が存在しない場合、取得APIはエラーではなく `null` を返す方針とする。

対象API：

* API-101 食事記録取得
* API-201 体調記録取得
* API-301 筋トレ記録取得

理由：

* 未登録日は正常な利用ケースである
* フロントエンドでは空フォームを表示する必要がある
* 404として扱うより、画面側の制御が明確になる

日次詳細APIでは、各記録単位で `null` を返す。

例：

```json
{
  "date": "2026-07-08",
  "meal": null,
  "condition": null,
  "workout": null
}
```

詳細なレスポンスschemaはSwagger / OpenAPIで管理する。

---

## 9. 削除APIの扱い

日次記録の削除は、日付単位の一括削除とする。

対象API：

* API-403 日次記録一括削除

削除対象：

* 食事記録
* 体調記録
* 筋トレ記録

設計方針：

* 指定日の記録をまとめて削除する
* 個別削除は今回対象外とする
* 削除成功時はレスポンスボディを返さない
* 削除後の画面更新方針は状態管理・データフロー設計書で扱う

削除対象が存在しない場合の扱いは、冪等性を重視して成功扱いとする方針を基本とする。
最終的なステータスコードはSwagger / OpenAPIおよびバリデーション・エラー設計書で管理する。

---

## 10. レスポンスに含める情報の方針

APIレスポンスでは、画面表示およびフロントエンド制御に必要な情報を返す。

基本方針：

* 画面表示に必要な記録データを返す
* 内部管理用の情報は必要最小限にする
* 認証済みユーザーの識別子を、画面表示目的で不用意に返さない
* `createdAt` / `updatedAt` を返すかどうかは、画面利用・デバッグ・将来拡張を踏まえて判断する

詳細なレスポンス項目はSwagger / OpenAPIを正とする。
レスポンスに `userId` を含めるかどうかは、認証・認可設計書およびデータ項目定義書で確認する。

## 11. ステータスコード方針

| ステータス | 用途                           |
| ----- | ---------------------------- |
| 200   | 取得成功、更新成功                    |
| 201   | 新規作成成功                       |
| 204   | 削除成功                         |
| 400   | リクエスト形式不正、バリデーションエラー         |
| 401   | 未認証                          |
| 403   | 認証済みだが権限がない                  |
| 404   | APIパス不正、またはエラーとして扱うべきリソース未存在 |
| 500   | 想定外のサーバーエラー                  |

補足：

* 記録が未登録であることは通常ケースとして扱い、原則として404にはしない
* 作成と更新を同一APIで扱う場合、201と200の使い分けは実装・OpenAPI側で明確化する
* 削除対象が存在しない場合は、冪等性を重視して成功扱いにする方針を基本とする

---

## 12. エラー方針

APIエラーは、フロントエンドが扱いやすい形式で返す。

共通エラーとして扱う主なケースは以下。

* 認証されていない
* 権限がない
* 日付形式が不正
* 必須項目が不足している
* 数値形式が不正
* 入力値が許容範囲外
* メモ文字数が上限を超えている
* 存在しないAPIにアクセスした
* サーバー内部で想定外のエラーが発生した

共通エラーレスポンス形式、エラーコード、ユーザー向けメッセージ、画面表示方針は、バリデーション・エラー設計書で扱う。

---

## 13. API変更時の管理方針

APIはフロントエンドとバックエンドの契約であるため、変更時には影響範囲を確認する。

API変更時に確認する対象は以下。

* 使用画面
* API client
* hooks
* フロントエンド型定義
* Swagger / OpenAPI
* バリデーション
* テスト
* 認証・認可処理
* エラー表示

破壊的変更が発生する場合は、以下を確認する。

* エンドポイント変更
* メソッド変更
* request body変更
* response body変更
* status code変更
* 認証方式変更
* エラー形式変更

---

## 14. 詳細スキーマの管理方針

詳細なAPI仕様はSwagger / OpenAPIを正とする。

本ドキュメントでは、リクエスト・レスポンスの全項目を重複管理しない。

管理分担は以下とする。

| 内容                | 管理場所                  |
| ----------------- | --------------------- |
| API全体方針           | API設計書                |
| API一覧             | API設計書 / Swagger      |
| endpoint / method | Swagger / OpenAPI     |
| request schema    | Swagger / OpenAPI     |
| response schema   | Swagger / OpenAPI     |
| DTO               | バックエンド実装              |
| フロントエンド型          | フロントエンド実装またはOpenAPI生成 |
| 画面とAPIの対応         | API設計書 / 画面設計書        |
| エラー表示             | バリデーション・エラー設計書        |
| 認証方式              | 認証・認可設計書              |
| 状態管理              | 状態管理・データフロー設計書        |

Swagger / OpenAPIと実装が乖離しないように、API変更時にはSwagger定義も更新する。
