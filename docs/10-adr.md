# 健康管理マスター ADR / 設計判断メモ v0.1

## 1. ドキュメントの目的

本ドキュメントは、健康管理マスターの設計・実装において行った重要な技術判断と、その判断理由を記録するための資料である。

本ドキュメントでは、単なる採用技術の一覧ではなく、以下を残す。

* どのような課題や選択肢があったか
* 何を採用したか
* なぜその判断をしたか
* 採用によってどのような利点・制約が生じるか
* どのような状況になったら再検討するか

この記録により、将来設計を変更する際に、過去の判断理由を確認できるようにする。

---

## 2. ADRの運用方針

## 2.1 ADRとは

ADRは `Architecture Decision Record` の略であり、アーキテクチャや実装方針に関する重要な意思決定を記録する。

ADRには、以下のような判断を記録する。

* システム構成
* 認証方式
* API設計方針
* データモデル方針
* 状態管理方針
* セキュリティ方針
* 将来の変更に大きく影響する技術選択

画面上の細かな文言や、CSSの調整などは原則としてADRの対象外とする。

## 2.2 ステータス

ADRでは、以下のステータスを利用する。

| ステータス      | 意味                |
| ---------- | ----------------- |
| Proposed   | 検討中               |
| Accepted   | 採用済み              |
| Rejected   | 検討したが不採用          |
| Deprecated | 現在は推奨しない          |
| Superseded | 新しいADRによって置き換えられた |

## 2.3 変更時の扱い

過去のADRは、原則として削除しない。

設計判断が変わった場合は、以下のように扱う。

```text
既存ADR:
StatusをSupersededへ変更する

新規ADR:
新しい判断内容を別番号で追加する
```

これにより、設計変更の経緯を追跡できるようにする。

# ADR-001：フロントエンドとバックエンドを分離したSPA構成を採用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

健康管理マスターは、以下の要素で構成される。

* Reactによるフロントエンド
* NestJSによるバックエンドAPI
* 認証・認可
* DB設計
* AWSへのデプロイ
* フロントエンドとバックエンドの責務分離

フロントエンドとAPIを分離することで、画面とAPIの責務を分け、片方の変更が他方へ波及しにくい構成にできる。サーバーサイドでHTMLを生成する構成に比べ、クライアントの多様化やデプロイ単位の分離にも対応しやすい。

## 検討した選択肢

| 選択肢                    | 内容                   |
| ---------------------- | -------------------- |
| React SPA + NestJS API | フロントエンドとバックエンドを分離する  |
| Next.js等のフルスタック構成      | 画面・APIを同じフレームワーク内に置く |
| サーバーサイドレンダリング中心        | サーバーが画面HTMLを生成する     |

## 決定

以下の構成を採用する。

```text
Frontend:
React + TypeScript + Vite

Backend:
NestJS + TypeScript

Database:
PostgreSQL + Prisma

Communication:
REST API
```

フロントエンドはReact RouterによるSPAとし、バックエンドはJSON APIを提供する。

## 理由

* フロントエンドとバックエンドの責務を明確にできる
* ルーティング・状態管理・API通信をフロントエンド側に集約できる
* Controller / Service / Guardによる責務分離を標準機構で実現できる
* 将来的にWeb以外のクライアントを追加しやすい
* AWS上でフロントエンドとバックエンドを別々に配置しやすい

## 結果・制約

* フロントエンドとバックエンド間でAPI契約が必要になる
* CORS設定が必要になる
* 認証tokenをAPIへ送信する設計が必要になる
* フロントエンドとバックエンドをそれぞれビルド・デプロイする必要がある

## 再検討条件

以下の場合は、Next.js等のフルスタック構成を再検討する。

* SSRやSEOが重要になる
* サーバーコンポーネントを利用したい
* フロントエンドとAPIを別々に管理する負荷が大きくなる

# ADR-002：APIはREST形式とし、詳細仕様の正本をSwagger / OpenAPIとする

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

API設計書にすべてのrequest / response項目を記載すると、実装変更時にSwaggerとMarkdownの二重管理が発生する。

APIの詳細項目は、実装の進行に伴って変更される可能性が比較的高い。

## 検討した選択肢

| 選択肢                        | 内容                                |
| -------------------------- | --------------------------------- |
| Markdownのみ                 | API仕様をすべてMarkdownで管理する            |
| Swagger / OpenAPIのみ        | API仕様をSwaggerで管理する                |
| API方針書 + Swagger / OpenAPI | 方針をMarkdown、詳細schemaをSwaggerで管理する |
| GraphQL                    | 単一endpointとschemaでAPIを提供する        |

## 決定

APIはREST形式とする。

管理分担は以下とする。

```text
API設計書:
API全体方針
API一覧
画面とAPIの対応
主要な設計判断

Swagger / OpenAPI:
endpoint
HTTP method
query parameter
request body
response body
status code
schema
認証方式
```

詳細なAPI仕様の正本はSwagger / OpenAPIとする。

## 理由

* NestJSとSwaggerの親和性が高い
* 実装とAPI仕様を近い位置で管理できる
* Markdownとの二重管理を減らせる
* フロントエンド開発者がAPI仕様を確認しやすい
* 将来的にOpenAPIから型生成できる

## 結果・制約

* Swagger定義を実装変更時に更新する必要がある
* API設計書には詳細schemaを重複記載しない
* 本番環境ではSwaggerの公開範囲を制限する必要がある

## 再検討条件

以下の場合はAPI方式を再検討する。

* 複雑な関連データを画面ごとに柔軟に取得する必要が増える
* GraphQL採用の明確な利点が生じる
* 複数クライアント向けのAPI version管理が必要になる

# ADR-003：認証基盤にAmazon Cognito User Poolを採用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

認証を完全に自作すると、以下の責務をアプリケーション側で持つ必要がある。

* パスワード保存
* パスワードハッシュ化
* パスワードリセット
* メール確認
* token発行
* refresh token管理
* token失効
* 不正ログイン対策
* MFA

認証基盤自体は自作せず外部サービスへ委譲し、認証済みユーザーを前提としたアプリケーション設計に注力する方針とする。

## 検討した選択肢

| 選択肢                     | 内容                  |
| ----------------------- | ------------------- |
| Amazon Cognito          | AWSのマネージド認証サービス     |
| 完全独自JWT認証               | NestJSとDBで認証基盤を自作する |
| Auth0等の外部認証サービス         | AWS外の認証サービスを利用する    |
| Firebase Authentication | Firebaseの認証基盤を利用する  |

## 決定

認証基盤にAmazon Cognito User Poolを採用する。

## 理由

* パスワードをアプリケーションDBで管理しなくてよい
* CognitoがJWTを発行する
* AWS構成との親和性が高い
* 実務で利用経験のある構成に近い
* 将来的にMFAや外部IDプロバイダーへ拡張できる

## 結果・制約

* Cognito固有の設定・用語を理解する必要がある
* User Pool、App Client、Managed Loginの設定が必要になる
* Cognitoのtoken claimとアプリケーションUserを紐づける必要がある
* ローカル開発でもCognito環境が必要になる

## 再検討条件

以下の場合は認証基盤を再検討する。

* AWSから別クラウドへ全面移行する
* Cognitoでは実現しにくい高度な認証要件が発生する
* 認証基盤を共通化した別サービスが導入される

# ADR-004：ログインにはCognito Managed LoginとAuthorization Code Grant + PKCEを利用する

> 用語について: 本ADRで「Managed Login」と記載しているものは、旧称「Hosted UI」と同一の機能を指す。
> AWS側の名称変更に伴い、`04-auth-design.md` の「1.1 用語」に従って表記を統一した。決定内容そのものに変更はない。

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

独自ログイン画面を実装すると、フォーム・認証エラー・パスワードリセットなどの実装範囲が増える。

今回の初期方針では、認証機能を素早く完成させ、アプリケーション本体の実装を優先する。

## 検討した選択肢

| 選択肢               | 内容                      |
| ----------------- | ----------------------- |
| Cognito Managed Login | Cognitoが提供するログイン画面を利用する |
| 独自UI + Cognito    | React側でログイン画面を作成する      |
| BFF経由のログイン        | NestJS経由でCognito認証を行う   |

## 決定

以下の構成を採用する。

```text
ログイン画面:
Cognito Managed Login

OAuthフロー:
Authorization Code Grant + PKCE

フロントエンド連携:
Amplify Auth

App Client:
public client

Client Secret:
利用しない
```

## 理由

* ログイン画面を自作する必要がない
* SPAでclient secretを安全に保持できない
* PKCEによりpublic client向けの認証フローを利用できる
* Amplify Authに認証状態・token取得処理を委ねられる
* 初期実装を短期間で完成させやすい

## 結果・制約

* ログイン時にCognito Managed Loginへ画面遷移する
* ログイン画面のデザイン自由度は低くなる
* Callback URLとLogout URLを環境ごとに設定する必要がある
* 独自ログイン画面の実装経験は今回得られない

## 再検討条件

以下の場合は独自UIを再検討する。

* ログイン画面のブランド・UX要件が強くなる
* Managed Loginでは実現できない画面制御が必要になる
* 認証フローをアプリ内で完結させる必要がある

# ADR-005：API認証にはCognito Access Tokenを利用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

CognitoからはAccess Token、ID Token、Refresh Tokenが発行される。

API認可にどのtokenを利用するかを明確にする必要がある。

## 検討した選択肢

| 選択肢            | 内容                 |
| -------------- | ------------------ |
| Access Token   | APIアクセスの認可用token   |
| ID Token       | ユーザー属性を含むtoken     |
| Cookie Session | Cookieによるサーバーセッション |

## 決定

API認証にはCognito Access Tokenを利用する。

フロントエンドは、以下の形式でAPIへ送信する。

```http
Authorization: Bearer <access_token>
```

バックエンドはJWTを検証し、`sub` claimから認証済みユーザーを特定する。

ID TokenはAPI認可には利用しない。

## 理由

* Access TokenはAPIアクセス認可を目的とするtokenである
* ID Tokenにはユーザー属性が含まれ、API認可の主用途ではない
* Bearer Token方式はREST APIと相性がよい
* React SPAとNestJS APIの分離構成に適している

## 結果・制約

* API clientがAccess Tokenを取得・付与する必要がある
* NestJS側でJWT署名・issuer・client_id・token_use等を検証する必要がある
* token期限切れ時の認証状態管理が必要になる

## 再検討条件

以下の場合はCookie SessionまたはBFF構成を再検討する。

* JavaScriptからtokenへアクセスさせない要件が強くなる
* セキュリティ要件が大幅に強化される
* フロントエンドからバックエンドへの通信をBFF経由に統一する

# ADR-006：CognitoのsubとアプリケーションUserを紐づける

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

Cognito上のユーザーと、アプリケーションDBの記録データを紐づける方法を決める必要がある。

emailやCognito usernameは、設定変更やユーザー属性変更の影響を受ける可能性がある。

## 検討した選択肢

| 選択肢         | 内容                       |
| ----------- | ------------------------ |
| Cognito sub | Cognitoが発行する一意識別子        |
| email       | メールアドレス                  |
| username    | Cognito User Pool上のユーザー名 |

## 決定

Cognitoの `sub` を外部認証IDとして利用する。

```text
Cognito sub
↓
User.cognitoSub
↓
User.id
↓
Meal / Condition / Workout
```

記録データはアプリケーション内部の `User.id` に紐づける。

## 理由

* `sub` はCognitoユーザーの安定した一意識別子である
* email変更の影響を受けにくい
* Cognito usernameの設定差異に依存しない
* アプリケーション内部IDと外部認証IDを分離できる

## 結果・制約

* `User.cognitoSub` に一意制約が必要になる
* APIアクセス時にsubからUserを検索する必要がある
* フロントエンドからuserIdを受け取らない
* Userが未作成の場合の作成処理が必要になる

## 再検討条件

原則として再検討しない。

認証基盤をCognito以外へ変更する場合は、外部認証IDの持ち方を再設計する。

# ADR-007：初回APIアクセス時にアプリケーションUserを作成する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

Cognito UserとアプリケーションDBのUserを同期するタイミングを決める必要がある。

## 検討した選択肢

| 選択肢         | 内容                          |
| ----------- | --------------------------- |
| 初回APIアクセス時  | JWT検証後、Userがなければ作成する        |
| Cognitoトリガー | サインアップ・ユーザー作成時にLambda等で作成する |
| 管理者による手動登録  | CognitoとDBの両方へ手動登録する        |
| 専用同期API     | ログイン後に明示的にUser作成APIを呼ぶ      |

## 決定

初回APIアクセス時に、`cognitoSub` に一致するUserが存在しない場合は自動作成する。

## 理由

* Cognitoトリガーを追加せずに実装できる
* 初期構成を単純に保てる
* 認証後に必ずバックエンド側でUserを解決できる
* CognitoとアプリDBの二重手作業を避けられる

## 結果・制約

* 最初の認証必須APIアクセス時にUser作成が発生する
* 同時アクセスによる重複作成を一意制約で防ぐ必要がある
* emailやnameをどのclaimから取得するか整理が必要になる
* User作成と通常処理の責務分離が必要になる

## 再検討条件

以下の場合はCognitoトリガー方式を再検討する。

* サインアップ直後に初期データを作成する必要がある
* User作成時に外部サービス連携が必要になる
* CognitoとDBの同期保証が重要になる

# ADR-008：初期状態管理にはReact標準機能を利用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

API取得・フォーム・認証状態を管理する方法として、React標準機能または外部ライブラリを選択する必要がある。

## 検討した選択肢

| 選択肢                            | 内容            |
| ------------------------------ | ------------- |
| useState / useEffect / Context | React標準機能     |
| TanStack Query                 | サーバー状態管理ライブラリ |
| Redux Toolkit                  | グローバル状態管理     |
| Zustand                        | 軽量状態管理        |

## 決定

初期実装では、以下を利用する。

```text
ローカル状態:
useState

副作用・API取得:
useEffect

認証状態:
Context
```

TanStack Queryは初期実装では導入しない。

## 理由

* 画面数とAPI数が少ない
* 状態の依存関係が複雑ではない
* React標準機能で完結でき、追加依存を持たない
* 初期実装を素早く完成させられる
* ライブラリ追加による依存・保守範囲の増加を避けられる

## 結果・制約

* ローディング・エラー・再取得処理を自前で管理する
* キャッシュ機能を持たない
* API取得ロジックが増えるとhookが複雑になる可能性がある
* 保存・削除後の再取得を明示的に実装する必要がある

## 再検討条件

以下の場合はTanStack Queryを導入する。

* API取得処理が増える
* キャッシュが必要になる
* 保存後のinvalidate処理が増える
* retryやstale timeの管理が必要になる
* ローディング・エラー管理の重複が増える

# ADR-009：初期フォーム管理にはuseStateを利用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

食事・体調・筋トレフォームの状態とバリデーションを管理する方法を決める必要がある。

## 検討した選択肢

| 選択肢                   | 内容                       |
| --------------------- | ------------------------ |
| useState              | React標準の状態管理             |
| React Hook Form       | フォーム管理ライブラリ              |
| React Hook Form + Zod | フォーム管理とschema validation |

## 決定

初期実装では、フォーム状態を `useState` で管理する。

FormStateでは数値入力もstringで保持し、保存時にnumberまたはnullへ変換する。

React Hook Form / Zodは将来課題とする。

## 理由

* 入力項目数が多すぎない
* 複雑なネストフォームではない
* HTML inputと数値変換の基本を理解できる
* 追加ライブラリなしで実装できる
* 初期実装を単純に保てる

## 結果・制約

* バリデーション処理を自前で実装する
* FormStateとAPI requestの変換処理が必要になる
* 項目数が増えた場合にコード量が増える
* エラーメッセージ管理が分散する可能性がある

## 再検討条件

以下の場合はReact Hook Form / Zodを導入する。

* フォーム項目が増える
* バリデーションが複雑になる
* 入力schemaを共有したい
* エラー管理の重複が増える
* 複数画面でフォームを再利用する

# ADR-010：API通信を共通API clientに集約する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

各画面から直接 `fetch` を呼び出すと、以下の処理が重複する。

* Base URL
* Authorizationヘッダー
* Content-Type
* query parameter
* JSON変換
* エラー処理
* response parse

## 検討した選択肢

| 選択肢             | 内容                   |
| --------------- | -------------------- |
| 画面から直接fetch     | 各Page・hookでfetchする   |
| 共通API client    | 通信共通処理を集約する          |
| Axios           | 外部HTTP clientを利用する   |
| OpenAPI生成client | OpenAPIからclientを生成する |

## 決定

fetchベースの共通API clientを作成する。

```text
Page
↓
custom hook
↓
resource API function
↓
apiClient
↓
Backend API
```

API clientは、Amplify AuthからAccess Tokenを取得し、Authorizationヘッダーへ付与する。

## 理由

* API通信の共通処理を一箇所に集約できる
* 画面コンポーネントの責務を減らせる
* 認証方式の変更に対応しやすい
* エラー形式を共通化できる
* 外部ライブラリを追加せずに実装できる

## 結果・制約

* API clientの責務が大きくなりすぎないよう注意が必要
* リソース固有の処理は別ファイルへ分離する
* 401処理とAuthContextの依存関係を整理する必要がある

## 再検討条件

以下の場合はOpenAPI生成clientまたはAxiosを検討する。

* API数が大幅に増える
* request / response型の手動管理が負担になる
* interceptor等の高度な通信処理が必要になる
* OpenAPIとの型同期を自動化する

# ADR-011：記録はユーザーごと・日付ごとに1件とする

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

食事・体調・筋トレ記録を、同じ日に複数件保存できるようにするか決める必要がある。

今回のアプリでは、日ごとの集計値やメモを管理する。

## 検討した選択肢

| 選択肢   | 内容                    |
| ----- | --------------------- |
| 1日1件  | 同一日の記録を上書きする          |
| 1日複数件 | 食事・計測・トレーニングごとに複数登録する |

## 決定

以下の記録は、1ユーザーにつき1日1件とする。

* Meal
* Condition
* Workout

DBでは、以下の一意制約を設定する。

```text
userId + recordDate
```

保存処理は登録・更新をまとめたupsertとして扱う。

## 理由

* 日次集計値を管理するアプリである
* 画面とAPIを単純にできる
* 履歴画面で日付単位に確認しやすい
* 同一日レコードの重複を防げる

## 結果・制約

* 食事ごとの明細は保存できない
* 1日に複数回行った筋トレを個別データとして扱えない
* 同一日の保存は既存値の上書きになる

## 再検討条件

以下の場合は1日複数件モデルを再検討する。

* 朝・昼・夕食を分けて管理する
* 食材単位で記録する
* 筋トレ種目・セット単位で管理する
* 1日内の時系列分析が必要になる

# ADR-012：記録日の境界をJST午前5時とする

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

深夜0時を過ぎてから食事・筋トレ記録を入力する場合、実生活上は前日の記録として扱いたいことがある。

一般的な日付の0時切り替えでは、生活日の感覚と記録日がずれる可能性がある。

## 検討した選択肢

| 選択肢    | 内容                |
| ------ | ----------------- |
| 0時境界   | カレンダー日付どおりに切り替える  |
| 3時境界   | 深夜帯を前日扱いにする       |
| 5時境界   | 早朝まで前日扱いにする       |
| ユーザー設定 | ユーザーごとに境界時刻を変更できる |

## 決定

記録日の境界を日本時間の午前5時とする。

```text
JST 00:00〜04:59:
前日扱い

JST 05:00以降:
当日扱い
```

API・DB上の `recordDate` は時刻を持たない日付として扱う。

## 理由

* 深夜の食事・トレーニングを前日の生活記録として扱える
* ユーザーの生活感覚に合っている
* 記録日の判断を一意にできる

## 結果・制約

* 通常のカレンダー日付と記録日が異なる時間帯がある
* フロントエンドの日付算出処理に専用ロジックが必要になる
* タイムゾーンを明示的に扱う必要がある
* テストで午前5時前後の境界値を確認する必要がある

## 再検討条件

以下の場合はユーザー設定化を検討する。

* 複数ユーザーが利用する
* 夜勤など生活時間の異なる利用者が増える
* 海外タイムゾーン対応が必要になる

# ADR-013：部分入力を許可し、完全空の記録保存を禁止する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

健康記録では、毎日すべての項目を入力できるとは限らない。

一方で、recordDate以外がすべて空のレコードを保存すると、履歴上は「記録あり」と表示されるが、実際の内容が存在しない状態になる。

## 検討した選択肢

| 選択肢     | 内容                |
| ------- | ----------------- |
| 全項目必須   | すべて入力しなければ保存不可    |
| 部分入力許可  | 1項目以上入力されていれば保存可  |
| 完全空保存許可 | recordDateのみでも保存可 |

## 決定

食事・体調記録は部分入力を許可する。

ただし、recordDate以外の全項目が空の場合は保存を許可しない。

筋トレ記録は、保存する場合にmemoを必須とする。

## 理由

* 日によって入力できる項目が異なる
* 入力負担を減らせる
* 完全空レコードの保存を防げる
* 履歴上の「記録あり」の意味を保てる

## 結果・制約

* DB項目の多くをnullableにする必要がある
* フロントエンドとバックエンドの両方で全項目空チェックが必要になる
* `0` と未入力を区別する必要がある
* FormStateとAPI requestの変換が必要になる

## 再検討条件

以下の場合は必須項目を再検討する。

* 分析上必須となる項目が発生する
* レポート生成に最低限必要な値が決まる
* 入力データ品質を強化する必要がある

# ADR-014：筋トレ記録は初期実装では自由テキストとする

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

筋トレ記録を構造化する場合、以下のデータモデルが必要になる。

* 種目
* 重量
* 回数
* セット数
* RPE
* 部位
* 実施順
* トレーニング時間

初期実装でこれらを扱うと、画面・API・DBの設計範囲が大きくなる。

## 検討した選択肢

| 選択肢            | 内容                   |
| -------------- | -------------------- |
| 自由テキスト         | 1日の筋トレ内容をmemoに記録する   |
| 構造化            | 種目・重量・回数・セット数を個別保存する |
| 自由テキスト + 一部構造化 | メモに加えて時間や部位を保存する     |

## 決定

初期実装では、筋トレ記録を自由テキストとして保存する。

## 理由

* 実装範囲を小さくできる
* 多様なトレーニング内容を柔軟に記録できる
* 先に日次記録・認証・AWS構成を完成させられる

## 結果・制約

* 種目別・重量別の集計ができない
* トレーニング分析が難しい
* 入力内容の表記が統一されない

## 再検討条件

以下の場合は構造化を検討する。

* 種目ごとの推移を表示する
* 重量・回数・セット数を分析する
* 筋トレメニューを再利用する
* トレーニング履歴検索が必要になる

# ADR-015：削除は日付単位の一括削除とする

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

記録削除について、食事・体調・筋トレを個別に削除するか、日付単位でまとめて削除するか決める必要がある。

## 検討した選択肢

| 選択肢         | 内容                                 |
| ----------- | ---------------------------------- |
| 日次一括削除      | 指定日の全記録をまとめて削除する                   |
| 記録種別ごとの個別削除 | Meal / Condition / Workoutを個別に削除する |
| 論理削除        | DB上にデータを残し削除フラグを設定する               |

## 決定

初期実装では、指定日の以下の記録を一括削除する。

* Meal
* Condition
* Workout

個別削除と論理削除は採用しない。

## 理由

* 現在の画面仕様が日付単位である
* APIと画面操作を単純にできる
* 個人利用アプリで監査要件がない
* 削除操作を一箇所にまとめられる

## 結果・制約

* 食事記録だけを削除することはできない
* 削除前の確認表示が必要になる
* 誤削除後に復元できない
* 削除後に月次履歴を再取得する必要がある

## 再検討条件

以下の場合は個別削除・論理削除を検討する。

* 記録種別ごとの削除需要が増える
* 誤削除からの復元が必要になる
* 監査ログや履歴保持が必要になる
* 複数ユーザー運用で削除追跡が必要になる

# ADR-016：初期実装ではAmplify Auth標準のtoken管理を利用する

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

SPAにおけるtoken管理には、以下の選択肢がある。

* localStorage
* sessionStorage
* memory
* JavaScriptから参照可能なCookie
* HttpOnly Cookie + BFF

セキュリティを最大限に重視する場合、ブラウザJavaScriptへtokenを公開しないBFF構成が有力である。

一方、BFF構成は初期実装の範囲を大きくする。

## 検討した選択肢

| 選択肢                   | 内容                        |
| --------------------- | ------------------------- |
| Amplify Auth標準管理      | Amplifyにセッション・token更新を委ねる |
| sessionStorage        | タブ単位でtokenを保存する           |
| memory                | リロードで消えるメモリ上に保存する         |
| HttpOnly Cookie + BFF | バックエンドでtokenを管理する         |

## 決定

初期実装では、Amplify Authの標準的なtoken管理を利用する。

refresh token管理・token更新を自作しない。

BFF + HttpOnly Cookieは将来課題とする。

## 理由

* Cognito Managed LoginとAmplify Authを短期間で連携できる
* token更新処理を自作しなくてよい
* 初期実装を素早く完成させられる
* 認証以外のアプリケーション設計に集中できる

## 結果・制約

* JavaScriptから参照可能な保存先を利用する場合、XSS成立時のtoken窃取リスクがある
* CSPやXSS対策が重要になる
* セキュリティ最優先の構成ではない
* token保存場所の実際の挙動を確認する必要がある

## 再検討条件

以下の場合はBFF + HttpOnly Cookie構成を検討する。

* 本番環境で高いセキュリティ要件が課される
* tokenをブラウザJavaScriptへ公開できない
* 個人情報・機微情報をより厳格に扱う
* API通信をBFFへ集約する

# ADR-017：初期実装ではself sign-upとロール管理を導入しない

## ステータス

Accepted

## 決定日

2026-07-12

## 背景

初期利用者は本人のみであり、不特定多数のユーザー登録や複数権限の管理は必要ない。

## 検討した選択肢

| 選択肢            | 内容                     |
| -------------- | ---------------------- |
| self sign-up有効 | 利用者が自分で登録する            |
| 管理者作成          | Cognito管理画面からユーザーを作成する |
| ロール導入          | 管理者・一般ユーザー等を分ける        |
| ロールなし          | 認証済みユーザーを同一権限として扱う     |

## 決定

初期実装では、以下の方針とする。

```text
self sign-up:
無効

ユーザー作成:
Cognito管理画面から手動作成

ロール:
導入しない
```

## 理由

* 初期利用者が本人のみである
* サインアップ画面・メール確認・スパム対策が不要になる
* 管理者画面を実装する必要がない
* 認可設計を単純にできる

## 結果・制約

* Cognito管理画面からユーザーを作成する必要がある
* 不特定多数へサービス公開できない
* 管理者・閲覧者等の権限分離ができない

## 再検討条件

以下の場合はself sign-upとロールを導入する。

* 複数ユーザーへ公開する
* 管理者機能を追加する
* 記録共有・閲覧専用権限を追加する
* 利用者自身による登録が必要になる
