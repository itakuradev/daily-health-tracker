# 健康管理マスター バリデーション・エラー設計書 v0.1

## 1. ドキュメントの目的

本ドキュメントは、健康管理マスターにおける入力バリデーションおよびエラー処理の設計方針を整理するための資料である。

本ドキュメントでは、以下を定義する。

* バリデーションの基本方針
* フロントエンドとバックエンドの責務分担
* 入力項目ごとの制約
* エラー種別
* エラーメッセージ方針
* APIエラー形式
* 画面ごとのエラー表示方針
* 初期実装スコープ
* 将来課題

詳細なデータ項目の意味、型、単位はデータ項目定義書で扱う。
APIのエンドポイント、ステータスコード方針はAPI設計書で扱う。

---

## 2. バリデーション設計の基本方針

健康管理マスターでは、ユーザーが日々の記録を気軽に入力できることを重視する。

そのため、初期実装では厳しすぎる入力制約は設けず、明らかに不正な値のみを防ぐ。

基本方針は以下とする。

* 入力項目は原則として部分入力を許可する
* ただし、完全に空の記録保存は許可しない
* recordDateは必須とする
* 数値項目は数値として解釈できる値のみ許可する
* 負の値は原則として許可しない
* 体調スコアは1〜5の整数のみ許可する
* 文字列項目は最大文字数を設定する
* フロントエンドでも入力チェックを行う
* バックエンドでも必ず入力チェックを行う
* フロントエンドのチェックだけに依存しない
* ユーザー向けメッセージは簡潔で分かりやすくする

---

## 3. バリデーション責務分担

## 3.1 フロントエンドの責務

フロントエンドでは、ユーザーが入力中または保存前に気づけるように、画面上で簡易バリデーションを行う。

主な責務は以下。

* 必須項目の確認
* 数値変換できるかの確認
* 明らかな範囲外入力の確認
* 全項目空保存の防止
* 体調スコアの選択肢制御
* 文字数上限の確認
* エラーメッセージ表示
* 保存ボタンのdisabled制御

## 3.2 バックエンドの責務

バックエンドでは、APIとして受け取る値を必ず検証する。

主な責務は以下。

* request body / query parameterの形式確認
* recordDate形式の確認
* 認証済みユーザーの確認
* 数値型の確認
* 数値範囲の確認
* 文字数上限の確認
* 全項目空保存の防止
* 不正な値に対する400エラー返却
* 認証エラーに対する401エラー返却
* 認可エラーに対する403エラー返却

## 3.3 責務分担の考え方

```text id="validation-responsibility"
フロントエンド:
ユーザー体験のための事前チェック

バックエンド:
データ整合性とセキュリティのための最終チェック
```

フロントエンドでチェックしていても、バックエンドでは同じ前提を再確認する。

理由：

* フロントエンドのチェックは回避できる
* APIはブラウザ以外から直接呼ばれる可能性がある
* DBに不正データを保存しないため
* 認可チェックは必ずバックエンドで行う必要がある

## 4. 共通バリデーション

## 4.1 recordDate

| 項目  | 内容                    |
| --- | --------------------- |
| 対象  | 食事記録、体調記録、筋トレ記録、履歴API |
| 必須  | 必須                    |
| 形式  | `YYYY-MM-DD`          |
| 例   | `2026-07-08`          |
| 空値  | 不可                    |
| 不正時 | 400 Bad Request       |

バリデーション内容：

* 未指定ではないこと
* 空文字ではないこと
* `YYYY-MM-DD` 形式であること
* 実在する日付であること
* 初期実装では未来日は許可しない

エラーメッセージ例：

```text id="record-date-error"
記録日を正しく入力してください。
```

## 4.2 未来日の扱い

初期実装では、未来日の記録作成・更新は許可しない。

理由：

* 健康記録は実績データとして扱うため
* 未来日の誤入力を防ぐため
* 初期実装では予約入力・予定入力を扱わないため

```text id="future-date-policy"
許可:
今日以前の日付

不許可:
明日以降の日付
```

JST午前5時境界による「今日」の算出は、フロントエンドの日付処理方針に従う。

## 4.3 過去日の扱い

初期実装では、過去日の入力・編集に制限を設けない。

理由：

* 過去分を後から入力したいケースがある
* 個人利用アプリであり、厳密な締め処理が不要
* 初期実装をシンプルにするため

将来的に必要になった場合、編集可能期間の制限を検討する。

## 5. 空値の扱い

## 5.1 基本方針

未入力値は、保存時に `null` として扱う。

| 入力値          | 保存時の扱い |
| ------------ | ------ |
| 空文字 `""`     | `null` |
| 空白のみ `"   "` | `null` |
| 未入力          | `null` |
| `0`          | 数値の0   |
| `"0"`        | 数値の0   |

## 5.2 完全空保存の扱い

各記録では、recordDate以外の項目がすべて空の場合、保存を許可しない。

対象：

* Meal
* Condition
* Workout

理由：

* 完全に空の記録を保存しても意味が薄い
* 履歴画面で「記録あり」と表示される根拠が曖昧になる
* DB上に不要なレコードが増える

エラーメッセージ例：

```text id="all-empty-error"
少なくとも1項目は入力してください。
```

## 10. APIエラー設計

## 10.1 共通エラー形式

APIエラー時は、フロントエンドが扱いやすい形式で返す。

```json id="api-error-response"
{
  "statusCode": 400,
  "code": "VALIDATION_ERROR",
  "message": "入力内容を確認してください。",
  "details": [
    {
      "field": "calories",
      "message": "カロリーは0〜10000の整数で入力してください。"
    }
  ],
  "path": "/api/meals",
  "timestamp": "2026-07-08T00:00:00.000Z"
}
```

## 10.2 エラー項目

| 項目         | 型      | 必須 | 内容                |
| ---------- | ------ | -- | ----------------- |
| statusCode | number | 必須 | HTTPステータスコード      |
| code       | string | 必須 | アプリケーション内部のエラーコード |
| message    | string | 必須 | ユーザー向けまたは汎用メッセージ  |
| details    | array  | 任意 | 項目ごとのエラー詳細        |
| path       | string | 任意 | 発生したAPIパス         |
| timestamp  | string | 任意 | エラー発生日時           |

## 10.3 details項目

| 項目      | 型      | 必須 | 内容            |
| ------- | ------ | -- | ------------- |
| field   | string | 必須 | エラー対象の項目名     |
| message | string | 必須 | 項目単位のエラーメッセージ |

## 11. エラーコード設計

## 11.1 共通エラーコード

| code                  | HTTPステータス | 内容               |
| --------------------- | --------: | ---------------- |
| VALIDATION_ERROR      |       400 | 入力値が不正           |
| UNAUTHORIZED          |       401 | 未認証              |
| FORBIDDEN             |       403 | 権限なし             |
| NOT_FOUND             |       404 | 対象なし、または存在しないAPI |
| CONFLICT              |       409 | 一意制約違反などの競合      |
| INTERNAL_SERVER_ERROR |       500 | 想定外のサーバーエラー      |

## 11.2 バリデーション系エラーコード

| code                    | 内容         |
| ----------------------- | ---------- |
| INVALID_RECORD_DATE     | 記録日が不正     |
| FUTURE_DATE_NOT_ALLOWED | 未来日が指定された  |
| ALL_FIELDS_EMPTY        | 全項目が空      |
| INVALID_NUMBER          | 数値形式が不正    |
| OUT_OF_RANGE            | 許容範囲外      |
| INVALID_INTEGER         | 整数である必要がある |
| TEXT_TOO_LONG           | 文字数上限超過    |
| INVALID_CONDITION_SCORE | 体調スコアが不正   |

---

## 12. HTTPステータスコード方針

| ステータス | 用途                        |
| ----- | ------------------------- |
| 200   | 取得成功、更新成功                 |
| 201   | 新規作成成功                    |
| 204   | 削除成功                      |
| 400   | バリデーションエラー                |
| 401   | 未認証、token不正、token期限切れ     |
| 403   | 認証済みだが権限なし                |
| 404   | 存在しないAPI、またはエラー扱いのリソース未存在 |
| 409   | 一意制約違反などの競合               |
| 500   | 想定外のサーバーエラー               |

補足：

* 未登録日の記録取得はエラーではなく `null` を返す
* 削除対象が存在しない場合は、冪等性を重視して成功扱いとする
* 入力不正は原則として400を返す

## 13. フロントエンドのエラー表示方針

## 13.1 基本方針

フロントエンドでは、ユーザーが次に何をすればよいか分かる形でエラーを表示する。

基本方針：

* 技術的なエラー詳細をそのまま表示しない
* 入力項目に紐づくエラーは項目付近に表示する
* 画面全体に関わるエラーはフォーム上部または画面上部に表示する
* 認証エラーはログイン画面へ誘導する
* サーバーエラーは再試行を促す
* tokenや内部情報は表示しない

## 13.2 表示箇所

| エラー種別   | 表示箇所                  |
| ------- | --------------------- |
| 入力項目エラー | 対象入力欄の近く              |
| 全項目空エラー | フォーム上部                |
| 認証エラー   | ログイン画面へ遷移、必要に応じてメッセージ |
| 権限エラー   | 画面上部                  |
| 通信エラー   | 画面上部または対象エリア          |
| サーバーエラー | 画面上部                  |

## 13.3 メッセージ例

| ケース   | 表示メッセージ                      |
| ----- | ---------------------------- |
| 全項目空  | 少なくとも1項目は入力してください。           |
| 数値不正  | 数値を正しく入力してください。              |
| 保存失敗  | 保存に失敗しました。時間をおいて再度お試しください。   |
| 取得失敗  | データの取得に失敗しました。               |
| 削除失敗  | 削除に失敗しました。                   |
| 未認証   | ログインしてください。                  |
| 権限なし  | この操作を行う権限がありません。             |
| 通信エラー | 通信に失敗しました。ネットワーク環境を確認してください。 |

## 16. バックエンド実装方針

## 16.1 DTOバリデーション

バックエンドでは、DTO単位でバリデーションを行う。

NestJSでは、`class-validator` / `class-transformer` の利用を検討する。

バリデーション対象：

* query parameter
* request body
* path parameter
* 認証情報から取得したユーザー情報

## 16.2 Service層での追加チェック

DTOで表現しにくいルールは、Service層で確認する。

Service層で扱う例：

* 全項目空保存の防止
* 認証済みUserの存在確認
* userId + recordDateによる一意制御
* 削除対象が存在しない場合の扱い
* User自動作成時の整合性確認

## 16.3 Prismaエラーの扱い

Prismaのエラーをそのままフロントエンドへ返さない。

Prismaエラーは、アプリケーション用のエラー形式へ変換する。

例：

| Prismaエラー | 変換後                       |
| --------- | ------------------------- |
| 一意制約違反    | 409 CONFLICT              |
| 対象なし      | 必要に応じて404、または通常ケースとして扱う   |
| DB接続エラー   | 500 INTERNAL_SERVER_ERROR |

---

## 17. フロントエンド実装方針

## 17.1 保存前バリデーション

フロントエンドでは、保存ボタン押下時にフォーム値を検証する。

処理の流れ：

```text id="frontend-validation-flow"
フォーム入力
↓
保存ボタン押下
↓
FormStateをAPI requestへ変換
↓
バリデーション
↓
問題なければAPI送信
↓
問題があれば画面にエラー表示
```

## 17.2 エラーstate

フォームごとにエラーstateを持つ。

例：

```ts id="form-error-state"
type FormErrors = {
  [field: string]: string;
};
```

画面全体エラーは、フォーム項目エラーとは分離する。

```ts id="page-error-state"
type PageError = string | null;
```

## 17.3 APIエラーの扱い

API clientで受け取ったエラーは、画面側で表示用メッセージに変換する。

```text id="api-error-handling"
APIエラー
↓
ApiError型へ変換
↓
画面文脈に応じたメッセージへ変換
↓
表示
```

## 18. ログ出力方針

## 18.1 フロントエンド

初期実装では、開発中のみconsole出力を許可する。

本番環境では、以下を出力しない。

* Access Token
* ID Token
* Refresh Token
* Authorizationヘッダー
* 個人情報
* DB内部ID
* スタックトレース全文

## 18.2 バックエンド

バックエンドでは、エラー調査に必要な範囲でログを出力する。

出力してよい情報：

* エラー発生箇所
* HTTPステータス
* APIパス
* エラーコード
* request ID
* 発生日時

出力しない情報：

* Access Token
* ID Token
* Refresh Token
* パスワード
* Authorizationヘッダー全文
* 個人情報
* 詳細なDB接続情報
